## 1. 本阶段结论与目标

现有架构方向保留：

> 项目固化业务规则与状态机 → Skill 负责引导、选模式和解释结果 → GKD 只执行已验证的窄动作。

但当前不能进入日常自动运行，原因是：

1. mi14Pro 已本地安装本项目订阅 `82640113` v7，但项目订阅、全局规则匹配及 GKD 无障碍均关闭；无 v7 真机引擎命中记录。
2. 初版 `--observe` 曾可能切 Tab、滚动页面；本批次已改为无 UI 动作，并将“候选可见”与“业务完成”分开。
3. 初版部分流程把“按钮消失”或包含 `needs_review` 的运行记为成功；已收紧退出码，但完整同券身份还依赖页面可见证据。
4. 默认设备曾指向旧 OnePlus 13 序列号；已移除并改为单设备自动发现。
5. 项目 Skill 已在批次 1 建立；当前仍需人工走查，并统一旧文档与新规则开关口径。

本阶段目标不是“尽可能多点按钮”，而是形成一条可以审计的每日任务链：

```text
真机预检
  → 会员每日打卡
  → 当期等级礼包/无门槛券
  → 消费券双重补贴
  → 地区专享
  → 点亮/浏览并回场核验
  → 只读盘点积分兑券与即将过期权益
  → 输出购买前优惠建议（不自动下单）
```

## 2. 固定边界

- 不自动购买、提交订单、付款、退款或使用券。
- 不进入分享、拉人、砍价、视频流、抽福袋等裂变流程。
- 不为了积分、等级或凑门槛主动增加消费。
- 不把 ADB 点击成功、节点消失或普通 XML 命中当成领取成功。
- 第一版继续保持两种互斥模式，不在运行中自动切换执行器：
  - **GKD 辅助模式**：用户手动进页；GKD 只点已验收窄规则；脚本只观察。
  - **脚本任务模式**：人工确认本订阅全部拼多多自动点击规则（含 key1/key2 与 key5/key8）及第三方中所有重叠规则已关闭；脚本独占点击权。

## 3. 分阶段实施

### P0-A：修复只读性和结果语义

开发项：

1. 让所有 `--observe` 路径满足零 `tap`、零 `swipe`、零 `back`、零开关变更。
2. `needs_review` 必须返回非零退出码，并由上层原样传播。
3. 将“按钮消失”降级为 `needs_review`；只有同券出现明确的“已领取/去使用”、券包新增记录或等价正向证据才可记 `verified`。
4. 为 `verified / already_claimed / unavailable / failed / needs_review` 建立统一退出码和汇总语义。
5. 增加离线测试，覆盖观察模式无动作、结果传播和假成功回归。

验收：

- 用 mock helper 记录动作，所有 observe 用例动作计数为 0。
- 人工构造“目标消失但无领取态”，结果必须是 `needs_review`。
- 任一步 `needs_review` 时整条任务不得返回成功。

### P0-B：设备发现与运行前预检

开发项：

1. 移除业务主入口中的旧设备默认值；单设备时自动选择，多个设备时强制指定 `--serial`。
2. 添加根目录 `.python-version`，按当前项目明确 Python minor 版本。
3. 预检输出并核对：设备型号、序列号、分辨率、前台包名、拼多多/GKD 版本、无障碍状态。
4. 读取 GKD 可见数据库/文件，核对订阅 `82640113`、版本和最近命中记录；只读检查不得修改 GKD 私有数据。
5. 脚本任务模式继续要求人工确认重叠规则关闭，不能由 PC 锁替代。

验收：

- mi14Pro 可不依赖旧序列号启动观察。
- 未安装 v7、多个设备、前台非拼多多、无障碍关闭等情况均明确拒绝执行动作。

### P1：建立单一项目 Skill 入口

建议新增仓库内唯一 Skill：`.agents/skills/gk-pdd-coupon/SKILL.md`。

Skill 只负责：

1. 识别用户意图：每日领取、只读盘点、单项验收、购买前优惠分析。
2. 选择 GKD 辅助模式或脚本任务模式，并执行互斥检查。
3. 调用本仓权威入口，不调用旧 `claim_all.py`、淘宝任务或充值中心流程。
4. 将执行结果翻译成每日清单和待人工处理项。
5. 发现页面改版、目标歧义或未知弹窗时停止并输出 `needs_review`。

Skill 不保存业务选择器，不复制状态机逻辑；选择器和结果判断仍固化在本仓脚本与 `dist/gkd.json5`。

验收：

- Skill 中不出现“必然领全、全量扫荡、生产级闭环”等绝对表述。
- 同一请求只产生一个执行器；不得同时让 GKD 与 ADB 点击拼多多。

### P2：mi14Pro 脚本基线逐项验收

按风险从低到高逐项执行，每次只验一个业务步骤：

| 顺序 | 项目 | 必要正向证据 | 失败/停机条件 |
|---|---|---|---|
| 1 | 会员打卡 | 同一会员页出现当日完成态或积分可归因变化 | 仅“打卡”消失、候选不唯一 |
| 2 | 等级礼包券 | 同一卡片由“领取”变“已领取/去使用”，或券包新增对应券 | 只有其他券的已领态、同屏多候选无法关联 |
| 3 | 双重补贴 | 同券名称/门槛/有效期可关联的领取后状态 | 误进商品页、卡片身份不足 |
| 4 | 地区专享 | Tab 已切换且同券领取前后可关联 | 当前地区无资格、横滑后身份丢失 |
| 5 | 点亮浏览 | 完成要求时长后返回会场见“今日已点亮” | 浏览中离开前台、只完成计时无回场证据 |

每项至少完成三类样本：可领取、已领取/不可用、异常或歧义。未覆盖三类样本的步骤不能进入 GKD 验收。

### P4：每日权益盘点与购买前分析

新增只读报告，不自动兑换积分、不自动下单。建议输出：

1. 今日打卡状态、连续打卡进度和可得积分。
2. 已领取券：名称、金额、门槛、适用范围、有效期、来源。
3. 当前可领但未领项目及未领原因。
4. 积分余额与可兑换券；只有在存在购买计划时给兑换建议。
5. 即将过期券和使用限制。
6. 针对待购商品计算候选组合：

```text
真实节省 = 可信渠道同款基准价
         - 拼多多最终结算价
         - 会员费摊销
         - 为凑门槛增加的消费
         - 不可接受的售后/保修风险折价
```

购买建议必须到结算确认页为止，不点击“提交订单/付款”。需要用户提供或选择具体商品后，才进行跨平台同规格比价。
