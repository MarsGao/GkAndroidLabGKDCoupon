## 1. 审核结论

采用 **Skill 编排 + 确定性脚本管理流程 + GKD 执行已验证的局部规则**。不建议每次都让 AI 看屏逐步点击，也不建议把整条业务流程全部塞进 GKD。

短期先用脚本单独执行模式建立可靠基线，再接入 GKD 协作。效率来自稳定流程可以重复执行、失败能准确定位，而不是工具数量或自动点击数量。

保留个人项目 `GkAndroidLabGKDCoupon` 和订阅名「MarsGao薅羊毛领券」；继续只维护少量专用规则，不 fork 大型广告订阅。第三方订阅可以独立使用，但不能假设同屏规则天然互不干扰。

## 4. 方案比较与职责

| 方案 | 重复操作成本 | 适合场景 | 主要限制 | 决策 |
|---|---|---|---|---|
| AI 每步看屏点击，由 Skill 提示流程 | 每步观测和推理；延迟和成本待测 | 首次探索、改版、无节点页面 | 会话中断、推理偏移、结果口述替代验收 | 作为辅助接管 |
| 全部 GKD | 稳定节点动作无需每步 AI | 用户手动进页后的签到/单券领取 | 缺节点入口、多页业务恢复、业务结果统计维护复杂 | 保留窄规则 |
| Skill 调用确定性脚本 | 已知流程无需每步推理 | 导航、状态管理、浏览计时、逐券核验 | 需维护页面识别；完整执行通常需电脑/ADB | 第一阶段主执行模式 |
| 脚本与 GKD 受控协作 | 稳态节点交给手机规则 | 已验证规则的长期复用 | 交接不清会引入竞态，未必比单脚本更快 | 基线稳定后按收益接入 |

Skill 是任务入口和执行约定，本身不提供更可靠的屏幕观测。现有 `gk-android-ecommerce-coupon` 本轮作为被审对象读取，不运行其全平台调度命令。后续优先修订这一个项目技能，增加此次任务的窄入口，不再创建另一个争夺流程控制权的技能。

建议两种运行模式，第一版不要中途自动切换：

1. **GKD 辅助模式**：用户进入已支持页面，GKD 只执行验证过的局部规则。AI/ADB 只观察；不能宣称已自动完成整条任务。
2. **脚本任务模式**：先确认本订阅及其他订阅中重叠的拼多多点击规则已停用，脚本获得设备执行权，独立完成已批准任务。结束后恢复先前配置并回读。若无法可靠控制并核验规则开关，要求现场切换；不杜撰 GKD 控制 API，不直接改其私有数据库。

后续仅在明确证明收益时增加阶段交接：脚本导航 → 停止脚本点击 → GKD 局部处理 → 观察结果 → 确认 GKD 已暂停 → 脚本继续。等待超时不能直接并发补点。PC 进程锁只能挡住多个脚本，挡不住手机 GKD，因此不能把锁文件当作互斥已完成的证据。

## 5. 目标流程与成功定义

执行链：预检 → 识别当前位置 → 会员打卡 → 等级礼包 → 返回已识别主会场 → 消费券入口 → 双重补贴逐券处理 → 点亮与浏览任务 → 返回消费券会场 → 地区专享逐券处理 → 汇总。

这是规划的任务顺序；恢复执行以当前页面和已完成状态为准，不强行重做已领取步骤。每个步骤统一为：**观察 → 验证前置条件 → 定位唯一目标 → 单次动作 → 等待可观测变化 → 核验 → 记录结果**。

- 预检：显式设备、连接状态、屏幕解锁、前台包名、App/GKD 版本、分辨率及方向、订阅版本与执行模式。无障碍空树是观测失败，不能解释为已领完。
- 页面识别：包名只是第一层；通用 Activity 不能区别业务页。组合标题、Tab、卡片结构、弹窗和负例特征。截图与节点不一致时不点击。
- 入口：新鲜节点优先；当前 GKD 快照和 UIAutomator 都无有效节点时，再采用当前截图上的文字/图像辅助定位。旧 `(603,777)` 只保留为历史证据。
- 打卡：仍在会员页，且出现当日已打卡状态；积分变化可作辅助证据。「打卡」消失或看到未来的「待打卡」不单独构成成功。
- 等级券：确认等级礼包及目标无门槛券属于同一卡片；目标变已领取/去使用/已使用才记状态。页面已有其他已领取券不能导致全部跳过。
- 消费券：关联同一卡片的券名称、金额/门槛、有效期等可见属性；逐张重新定位。无法区分两个同名券时记录歧义，不能用坐标充当永久 ID。
- 点亮：进入明确浏览任务后开始计时，确认页面持续有效，按页面实际要求浏览（历史为 10 秒）。离开前台或被遮挡则暂停/重新核验；计时结束还需回到会场看到今日已点亮等完成证据。仅 `sleep(10)` 不算成功。
- 地区专享：先核验 Tab 已选中或内容区域确实切换，才找券。横滑/纵滑限于识别出的券区，不使用全屏固定 y。
- 停止条件：无新券且相邻快照重复、到达边界、达到时间/动作上限时停止遍历。区分“本次已观察范围处理完成”和“全部券领完”；没有覆盖证据不写后者。
- 异常：网络加载失败、通知遮挡、商品详情、分享/支付页、候选歧义、未知弹窗都停止当前点击队列。只允许一次已知路径的恢复尝试，恢复失败交给人工/AI诊断。
- 结果：`verified / already_claimed / unavailable / failed / needs_review`。前后证据不能对应到同一券时为 needs_review。应用显示领取状态是 UI 级验收，不夸大为服务器或最终可用额度证明。

持久化 checkpoint 只存阶段、规则版本、时间和脱敏券标识；恢复时必须重新观察。每日任务日期取活动页/适用业务时区，不直接采用当前电脑的 Europe/Berlin 日期；日期账本不能替代页面状态核验。

## 7. 测试与上线标准

离线测试覆盖：精确文本/desc、同屏多个领取按钮、券卡关联、旧坐标失效、空树、旧 dump、ADB 失败、已领取、无券、商品/分享弹窗、Tab 未切换、不同尺寸。用 GKD 选择器解析/快照审查验证规则语义，Python XML 扫描不能代替 GKD 引擎测试。

现场验收先固定 OnePlus 13 + 明确拼多多/GKD 版本，不推广为所有机型。普通规则至少 3 次独立场景执行及一次同日重跑；每日任务需跨两个实际业务日观察，不能靠重进 App 伪造次日验证。没有新券时只验证 already_claimed 分支，不算首次领取分支通过。

每轮记录：任务耗时、尝试数、可证明的成功数、未知结果数、误入页次数、人工介入数、AI 工具调用/用量。分别比较脚本基线与 GKD 协作，不预先声称节省某个百分比。错误领取或危险目标点击为零、所有成功有证据，是这批测试的通过条件；不代表未来版本绝不会误触。

发布前检查 id/version 一致、规则 key 稳定、正负快照回归、手机订阅回读、README 验证矩阵。截图和 XML 留本地；公开样例需人工确认脱敏。回滚需将上一份已验证内容以更高 version 发布，不能假设较低 version 会被手机自动接受。

## 8. 官方资料核对

- [GKD RawRuleProps](https://gkd.li/api/interfaces/rawruleprops)：matches 数组要求全部命中、动作指向最后一个选择器；这不意味着节点同属一张券卡。当前文档支持 `preKeys`、`swipe`、`swipeArg`，所以旧代码“GKD 无法滑动”的绝对结论应撤回；目标设备版本支持情况仍需核实。
- [GKD RawCommonProps](https://gkd.li/api/interfaces/rawcommonprops)：`resetMatch: 'app'` 为重新进入 App 重置，不是每日限额；匹配窗口会休眠，actionMaximum 为动作次数。配置需按真实进入路径验证。
- [GKD RawSubscription](https://gkd.li/api/interfaces/rawsubscription)：新版本号更大才更新；因此需验证手机实际导入版本，并设计递增版本回滚。
- [GKD 外部交互](https://gkd.li/guide/external)：已查看公开外部交互说明，不能据此假定存在已验证的按规则组动态启停 API。
